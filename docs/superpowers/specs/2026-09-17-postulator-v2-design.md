# Postulator v2 — Design Spec

Sections 1-10 and 15 of the approved plan, verbatim. This file is the contract;
the distilled docs in `docs/` point back here and never restate it.

---

## 1. Context

The current repo (v1.6.2) is a WordPress post generator written for the same client. Exploration found: one usable pattern (`StartX → taskID → Get/List/Cancel`), everything else unfit: Wails calls blocking for minutes, fire-and-forget event bus that never reaches the UI, no per-step persistence (crash leaves zombie rows and orphan WP posts), page map lacking H1/meta/anchors/page type, hierarchy stored three ways and drifting, SEO meta generated but never written to WP, secrets in plaintext, one test file in the whole repo. The code is discarded, not refactored.

The client (an SEO specialist, not a developer) has a network of WordPress sites (pages, posts, WooCommerce) with an Excel-based page map (slug, title, H1, keywords, anchors) and an Entity Graph. He wants pages generated so that internal links prove entity relationships: up to parents, down to own children, sideways only to explicitly related siblings, never outside the graph. He also wants to talk to local AI agents that can read his data, edit the graph and templates, run and monitor pipelines, and build a graph from scratch for a site that has nothing yet. The UI (canvas, reports) is built later with Claude Design against the Go contracts defined here.

## 4. Kernel (shared package)

- `kernel/errors` (port of Archond `internal/shared/errors/{errors,codes}.go` minus HTTP status): `type Code string` with frozen constants `NotFound, Conflict, Invalid, Unauthorized, RateLimited, BudgetExceeded, External, Internal, Cancelled, NeedsHuman, Locked`. `type Error struct { Code Code; Message string; Details map[string]any; Retry *RetryInfo; internal error; stack []uintptr }` with `Error()`, `Unwrap()`, `Is(target error) bool` comparing by `Code`. Constructors `New(code Code, msg string) *Error`, `Wrap(err error, code Code, msg string) *Error`; clone-and-mutate `WithInternal(err)`, `WithRetry(after time.Duration)`, `WithDetail(k string, v any)`. Helpers `CodeOf(err error) Code` (returns `Internal` for foreign errors), `IsCode(err error, code Code) bool`. *(Amended 2026-10-04: no stack is captured and `Stack` is gone, since nothing read it.)*
- `kernel/paging` (port of Archond `pkg/dbx/{page,keyset}.go` + `pkg/api/list.go`, jet replaced by squirrel): `type Cursor string` (opaque base64url JSON `{"o":<orderBy>,"d":<asc|desc>,"v":[<values>],"i":"<row id>"}`), `type Request struct { After, Before Cursor; Limit int }` (default 50, max 500, `Normalize()`), `type List[T any] struct { Items Slice[T]; Cursors Cursors{Next, Prev Cursor}; HasMore bool }` where `Slice[T]` marshals nil as `[]`. `SortKey[T]` with kinds `Text, Int, Time` (the UUID, enum, float and bool kinds had no caller and went on 2026-10-04) and a `literal()` coercer; `Keyset[T]{Keys []SortKey[T], IDColumn string}` builds the squirrel predicate `(k1, id) > (?, ?)` (or `<` for desc / `Before`), applies `ORDER BY` with id tie-break and `LIMIT n+1`; `Cut[T](rows []T, limit int, key func(T) []any, id func(T) string) List[T]`. `paging` is the one kernel package allowed to import squirrel; domain never uses it.
- `kernel/id`: `New() string`, `Valid(s string) bool` (UUID v4; helper shape as Archond `pkg/identifier/uuid.go`).
- `kernel/clock`: `type Clock interface { Now() time.Time }`, `System{}`, `Fake` with `Set/Advance`.
- `kernel/log` (port of Archond `pkg/logger/logger.go`): zap builder with console core + lumberjack file core, JSON vs console encoder switch, default fields `service, version`; redaction of keys `password, apiKey, token, authorization`; sinks `app.log` and `errors.log`.
- `kernel/settings` (port of Archond `internal/settings/constructors.go`, without DB overrides/pins): settings-as-code, `settings.Int("runs.workers", 2, settings.IntRange(1, 16))`, `settings.String`, `settings.Bool`, `settings.Duration`, each declared next to the code that reads it, validated and defaulted, persisted in the `settings` table, exposed to the UI through a generated schema.
- `kernel/ctx`: `WithActor/ActorFrom` (`user|agent|schedule`). *(Amended 2026-10-04: the run and conversation values had no reader and are gone.)*
- `kernel/dto`: `Time` (RFC3339 UTC string ↔ time.Time), `Sort{Field string; Desc bool}`, `ListRequest{Cursor string; Limit int; Sort *Sort}`.
- `kernel/middleware`: generic wrappers `func Recover[In, Out any](fn) fn`, `Audit(logger)`. *(Amended 2026-10-04: `Timeout` had no caller and is gone.)*

## 5. Domain Model

### 5.1 Site (`domain/site`)
`Site{ID, Name, BaseURL, SecretRef, Status(active|paused|error), Plugin PluginState{Installed bool, Version string, Capabilities []string, SEOPlugin string}, Defaults{TemplateID, LinkPolicyID, ModelProfiles map[Role]ModelRef}, CreatedAt, UpdatedAt}`. Invariant: `BaseURL` https unless `AllowInsecure`.

### 5.2 Entity Graph (`domain/graph`)
- `Entity{ID, SiteID, Name, Kind(hub|product|topic|category|custom), Intent, Keywords keyword.List, Anchors []Anchor, ScopeID *string, CanonicalPageID *string, Score float64, Source(import|user|ai), CreatedAt, UpdatedAt}`; `Anchor{Text, Source(user|ai), Weight}`. `keyword.List` is `[]{Text, Volume *int}` sorted by volume; the name is unique under `ScopeID`, the parent it was named under. *(Amended 2026-10-02.)*
- `Edge{ID, SiteID, FromEntityID, ToEntityID, Kind(parent|related), Weight float64, Source(import|user|ai), Status(approved|proposed|rejected), CreatedAt}`. `parent` is directed child→parent; `related` is stored with `FromEntityID < ToEntityID`.
- `Graph` value type built from entities+edges with pure methods: `Parents(id, depth)`, `Children(id)`, `Related(id, minWeight)`, `ValidateAcyclic() error`, `Score()` (PageRank-like over approved edges, damping 0.85, 30 iterations). *(Amended 2026-10-04: `Roots()`, which only tests read, is gone.)*
- Invariants: no self edges, no cycles on parent edges, edge endpoints in the same site.

### 5.3 Page Map (`domain/pagemap`)
- `Page{ID, SiteID, Path, Slug, ParentPageID *string, WPType(page|post|product|product_cat), WPID *int64, Title, H1, MetaTitle, MetaDescription, Canonical, Keywords keyword.List, Notes []{Label, Text}, Status(planned|exists|published|archived), EntityID *string, TemplateID *string, ContentHash, WPModifiedAt *time, LastSyncedAt *time, Drift bool, CreatedAt, UpdatedAt}`. A page's keywords win over its entity's; the notes come from an import's note columns. *(Amended 2026-10-02.)*
- `PageLink{ID, SiteID, FromPageID, ToPageID *string, ToURL, AnchorText, Origin(generated|observed), ObservedAt}`.
- Pure helpers: `NormalizePath`, `ParentPath`, `BuildTree(pages)`. *(`Unmapped` and `InternalPath` had no caller and went on 2026-10-04; `pagemap.Site.Resolve` classifies a link target.)*
- `Index` value type: `NewIndex(pages []Page) Index` with `ByID(id) (Page, bool)`, `ByEntity(entityID) []Page`, `ByPath(path) (Page, bool)`.
- Link target resolution: `Entity.CanonicalPageID → Page.Path`; entities without a canonical page are never link targets.
- `Cannibalization(candidate Page, entity graph.Entity, index Index, g graph.Graph) Verdict{Allowed bool, Evidence []Evidence{PageID, Path, Reason(same_primary_keyword|same_entity_canonical|path_conflict), EntityID}}` lives here since Phase 2 (moved from §6): it depends only on the page index and the entity graph, and `pages.Create`, `pages.MapToEntity` and the import preview call it. `InternalPath(href, siteHost) (path, internal)` classified a link target against the site host until `pagemap.Site.Resolve` took its place; `NormalizePath` is the one canonical path normaliser and the WordPress adapter and plugin implement its rules.

### 5.4 Templates and Link Policy (`domain/template`)
- `Template{ID, Scope(global|site), SiteID *string, Name, PageKind, Version int, Spec TemplateSpec, CreatedAt, UpdatedAt}`.
- `TemplateSpec{Sections []Section{Heading, Intent, TargetWords, Required bool, KeywordRules}, Tone, Length{Min, Max}, KeywordRules{PrimaryInTitle, PrimaryInH1, PrimaryInFirstParagraph bool, MaxDensity float64}, LinkRules{UpDepth int, DownLinks bool, SiblingMinWeight float64, MaxLinks, MaxPerTarget int, ParentLinkWithinParagraphs int, ChildrenSection bool}, MetaRules{TitlePattern, DescriptionMax int}, Images{Featured bool, Inline int, Source(ai|wpmedia|local)}, ModelProfiles map[Role]ModelRef, Recipe []StepSpec}`.
- `StepSpec{Name string, Enabled bool, Params map[string]any}`.
- `Resolve(base TemplateSpec, siteOverride, pageOverride json.RawMessage) (TemplateSpec, error)` implements RFC 7396 merge patch over the JSON form of the spec (Phase 2): overrides are stored as merge-patch documents, arrays are replaced wholesale, `null` removes a key, and the resolved spec must pass `Validate`. `TemplateSpec` and its nested structs carry camelCase JSON tags because that JSON is their persisted form.
- `LinkPolicy` is the `LinkRules` plus site-wide `ForbidExternal bool, ForbidSelf bool, AnchorStrategy(prefer_user|rotate)`.
- Starter templates (Hub, Product, Guide, Comparison, Category) live in `domain/template/seed/*.json`, embedded, loaded by migration seeding in the application layer. A spec's optional `product` block names what a product gets beside its description: a short description (`enabled`, `intent`, `targetWords`, `primaryKeyword`); the shipped Product template carries one. Attribute filling is retired (2026-10-20): a product's attributes are the store's and never written, and migration 0067 strips `product.specifications` from stored specs and overrides, which the strict decode would otherwise refuse.

### 5.5 Content (`domain/content`) — see section 6.

### 5.6 Runs (`domain/run`)
- `Run{ID, SiteID, Kind(generate|relink|audit|sync|import|custom), Status(queued|running|paused|completed|failed|cancelled), Targets []string, Recipe []StepSpec, TemplateVersion int, PublishMode(draft|publish), Budget{MaxUSD, MaxTokens}, Stats{Items, Done, Failed, Tokens, USD}, CreatedBy Actor, ParentRunID *string, CreatedAt, StartedAt, FinishedAt}`.
- `Item{ID, RunID, PageID, Status(pending|running|done|failed|skipped|needs_human), CurrentStep string, Attempts int, Error *string}`.
- `StepExec{ID, ItemID, Step string, Attempt int, Status(started|done|failed), InputHash string, ArtifactID *string, Tokens int, USD float64, StartedAt, FinishedAt, Error *string}`.
- `Artifact{ID, RunID, ItemID, Step string, Kind(html|json|image|report), Blob []byte, Size int, ExpiresAt *time}`.
- `Event{RunID string, Seq int64, Type string, At time.Time, Payload json.RawMessage}`.
- `type ArtifactKind string` (values listed in section 6). `StepContext{Run, Item, Page, Template TemplateSpec, Artifacts map[ArtifactKind]Artifact, Params map[string]any, Deps StepDeps}` where `StepDeps` bundles the ports a step may use (LLM client, WP client, image provider, repositories); `StepOutput{Artifacts []Artifact, Tokens int, USD float64, Events []Event}`.
- `Step` interface (consumer-side in runtime): `Name() string; Requires() []ArtifactKind; Produces() []ArtifactKind; Execute(ctx, *StepContext) (*StepOutput, error)`. `ValidateRecipe(steps map[string]Step, recipe []StepSpec) error` checks that every enabled step's `Requires` is produced earlier.

### 5.7 Schedules (`domain/schedule`)
`Schedule{ID, SiteID, Name, Cron string, Interval *time.Duration, TargetQuery TargetQuery{EntityID *string, Status, Limit int}, TemplateID, Recipe []StepSpec, PublishMode, Budget, Enabled, NextRunAt, LastRunID, CreatedBy}`. `NextAfter(now)` pure.

### 5.8 Settings (`domain/settings`)
Typed settings: `Proxy{URL, Enabled}`, `Retention{ArtifactDays int}`, `Concurrency{Workers int, PerSite int}`, `ModelProfiles`, `Security{MasterPasswordEnabled bool}`.

### 5.9 LLM catalog types (`domain/llm`)
`ModelRef{Provider, Model}`, `ModelInfo{Ref, ContextTokens, MaxOutputTokens, InputUSDPerM, OutputUSDPerM, RPM, TPM, SupportsStructured, SupportsImages, Reasoning bool}`, `Usage{Input, Output, Total int}`, `Cost(usage, info) float64`, `Role(writer|editor|linker|judge|chat|image)`. *(Amended 2026-10-03: `ModelInfo` also carries the cached-input, cache-write and four flex prices and no reasoning effort; `Usage` counts cached reads and cache writes inside `Input` and reasoning inside `Output`; `ServiceTier(default|flex)`; `Cost(usage, info, tier)`; `Allowance(effort)`; `PurposeRules` for the spend report; the provider is OpenAI.)*

## 6. Content Factory (`domain/content`)

- `Document`: wrapper around `*html.Node` (x/net/html) parsed from body HTML fragment. Methods: `TextNodes(skip func(*html.Node) bool) iter.Seq[*html.Node]`, `Paragraphs() []*html.Node`, `Headings() []*html.Node`, `Links() []Link{Href, Anchor, Node}`, `HTML() string`, `Hash() string` (sha256 of normalised HTML).
- `LinkTarget{EntityID, PageID, URL, Anchors []string, Relation(up|down|sibling), Required bool, Weight float64}`.
- `BuildLinkContext(g graph.Graph, pages pagemap.Index, entityID string, policy LinkPolicy) LinkContext`: up targets for depth 1..UpDepth (all `Required`), down targets for direct children with canonical pages, sibling targets for approved related edges with weight ≥ `SiblingMinWeight`. Self excluded. Deterministic ordering: up by depth, down by entity score desc, siblings by weight desc.
- `InsertLinks(doc *Document, lc LinkContext, policy LinkPolicy) InsertResult{Placed []Placement{Target, Anchor, ParagraphIndex}, Missing []LinkTarget, Decisions []Decision{Target, Anchor, Outcome(inserted|already_linked|anchor_not_found|cap_reached|forbidden_zone|position_rule), Detail string}}` (decision-per-candidate as in Archond `internal/modules/content/linking.go`): walks text nodes in document order, skips nodes inside `a`, `h1..h6`, `code`, `pre`, or attributes; case-insensitive rune-based match of any anchor of any unplaced target; first match wins; respects `MaxLinks`, `MaxPerTarget`, and `ParentLinkWithinParagraphs` (parent targets only match in paragraphs `< N`, others anywhere); splices `<a href>` preserving original text casing; idempotent (existing links to a target count as placed).
- `Cannibalization` moved to §5.3 (`domain/pagemap`) in Phase 2.
- `Compliance(doc, lc, policy, pageID) Report`: for every target: `satisfied|missing`; every `<a>` in doc classified `graph|self|external|unknown_internal`; anchor whitelist violations; counts. `Report{Items []Finding{Severity(info|warn|error), Code, Message, Details}, Score float64}`.
- `Structure(doc, primary string, secondary []string, spec TemplateSpec) Report`: primary keyword in title/H1/first paragraph, secondary coverage, density, word count vs `Length`, headings match `Sections`, HTML validity.
- `ContentDraft{Title, H1, Sections []DraftSection{Heading, HTML}, Summary}` is the structured-output schema for `generate_body`; `Assemble(draft) *Document`.
- `RepairRequest{ParagraphIndex int, Phrase string}` / `RepairResponse{Sentence string}` for `repair_links`.

Step catalog (implemented in `internal/runtime/steps`, each in its own file, each registered by name): `resolve_context, generate_body, generate_meta, insert_links, repair_links, generate_images, validate, judge, publish, relink_neighbors, sync_back, report`. Artifact kinds: `link_context, draft, body_html, meta, images, validation_report, judge_report, publish_result, relink_result, sync_result, final_report`.

Behaviour of each step:
- `resolve_context`: builds `LinkContext` from graph+pages; artifact `link_context`.
- `generate_body`: prompt from template spec, keywords, required anchor phrases (from `link_context`), `Structured[ContentDraft]` with writer profile; artifact `draft` + `body_html`.
- `generate_meta`: `Structured[Meta{Title, Description, Canonical, OG}]` with editor profile under `MetaRules`; artifact `meta`.
- `insert_links`: pure; artifact `body_html` (replaced) + placement list in `validation_report` seed.
- `repair_links`: for each `Missing` required target, ask model (linker profile) for one sentence containing an anchor at a paragraph index; re-run `InsertLinks`; max 2 iterations.
- `generate_images`: `ImageProvider` by template `Images.Source`; uploads to WP media; artifact `images` (ids, urls, alt).
- `validate`: `Compliance` + `Structure`; artifact `validation_report`; fails item if any `error` finding unless `Params.allow_errors`.
- `judge`: `Structured[JudgeReport{Score, Issues, Suggestions}]` with judge profile; artifact `judge_report`; never fails the item.
- `publish`: idempotent create/update in WP (lookup by `WPID`, then by slug+parent), sets status per `PublishMode`, writes SEO meta through the plugin when capability present; artifact `publish_result{WPID, URL, Status}`.
- `relink_neighbors`: for affected pages (up targets, children, siblings) fetch current content, compute missing edges only, `InsertLinks`, compare `ContentHash` before update, conflict → item `needs_human`; artifact `relink_result`.
- `sync_back`: re-read page, update `WPID, ContentHash, WPModifiedAt, PageLink` rows; artifact `sync_result`.
- `report`: aggregates all reports into `final_report` and updates `Run.Stats`.

## 7. Run Engine (`internal/runtime`)

Shapes ported from Archond `internal/infra/jobs/pipeline/{pipeline,checkpoint,definition,handler,daemon,repository}.go`, with the Asynq executor and credit reservations removed.

- Vocabulary: `Status(pending|running|waiting|paused|completed|failed|cancelled)`; each step returns `Transition(continue|wait|pause|complete|fail)` plus an optional `WakeAt` for `wait`; `Fault{Class(transient|exhausted|invalid|fatal), Code, Action(retry|pause|fail), Message, Reason}` with `Classify(err) Fault` mapping kernel error codes (`RateLimited/External/Cancelled → transient`, `BudgetExceeded → exhausted`, `Invalid/Unauthorized → invalid`, `NeedsHuman → pause`); `PauseReason(budget_exceeded|awaiting_confirmation|needs_human|user)`.
- Checkpoint: `type Checkpoint map[string]json.RawMessage` with generic `Get[T](cp, key) (T, bool, error)`, `Set[T](cp, key, v) error`, `MergedWith(other) Checkpoint`; stored as one JSON column per `Item`; large outputs go to `Artifact` rows and the checkpoint stores their ids.
- Definition/registry: `Definition{Kind, Steps []StepDef, Deadline time.Duration}`, `StepDef{Name, Requires, Produces []ArtifactKind, Retry RetryPolicy{Max int, Backoff func(attempt) time.Duration}, Timeout time.Duration, Run func(ctx, *StepContext) (Result, error)}`; `Registry.Register(def)` validates names, artifact dependencies, and retry bounds at startup and fails fast.
- Advance loop (`handler.go` shape, single process): `advance(itemID)` claims the item in one SQLite transaction by compare-and-swap on `advance_seq`, runs the current step under its timeout, classifies the outcome, persists the new item state + checkpoint + a `StepExec` row + an appended `Event`, and schedules the next advance (immediate, at `WakeAt`, or none if terminal). Each step is idempotent via `alreadyDone(itemID, step)` on `StepExec` and `InputHash` = sha256(step name, params, required artifact hashes, template version).
- Sweep daemon (`daemon.go` shape): every N seconds re-arms `DueWaiting` items (wall-clock `WakeAt` reached), reclaims `Stalled` items (lease expired: process died mid-step), and `Reap` fails runs past `DeadlineAt` and purges old terminal rows per retention. This is the whole crash-resume story; the start runs one sweep. *(Amended 2026-10-03: `Engine.Recover`, which only renamed it, is gone.)*
- `Engine{Enqueue(ctx, run) error; Pause(id, reason); Resume(id); Cancel(id); RetryStep(itemID)}` *(amended 2026-10-03: `Wake`, which only its own test called, is gone; the sweep wakes a waiting item)*; `Workers` (N from settings) pull runnable items with per-site concurrency limit, per-provider+model rate limiter (catalog RPM/TPM), and a run-scoped `context.CancelFunc` map.
- Budget: pre-flight `EstimateRun(run, template, catalog) Estimate{Tokens, USD}` from section lengths × profile prices; runtime accumulates `Stats.USD`; exceeding `Budget` returns `Fault{Class: exhausted}` → run paused with `PauseReason budget_exceeded` and event `run.budget_exceeded`.
- Confirmations inside runs: a step that needs approval (publish when the run was started by an agent in `confirm` mode) returns `Transition pause` with `PauseReason awaiting_confirmation` and a `PendingAction` row (section 8); `ResolveAction` resumes the item.
- Item-level failure never fails the run; run finishes `completed` with `Stats.Failed > 0`, or `failed` only if every item failed.
- Event log: `eventlog.Append(ctx, runID, type, payload) (seq int64)`, `List(runID, sinceSeq, limit)`; every append also publishes to the live bus consumed by the Wails bridge. Event types: `run.queued, run.started, run.paused, run.resumed, run.cancelled, run.completed, run.failed, run.budget_exceeded, item.started, item.done, item.failed, item.needs_human, step.started, step.done, step.failed, step.retrying, llm.usage`.
- Retention job: purges `Artifact.Blob` for `html|image` kinds older than `Retention.ArtifactDays` after `publish_result` succeeded; keeps reports and metadata.

## 8. Contracts (Wails v3, `internal/transport/wails`)

- Services: `SitesService, GraphService, PagesService, TemplatesService, RunsService, AgentService, ImportService, SchedulesService, ReportsService, SettingsService`. Thin: DTO mapping only.
- Method shape `func (s *X) Method(ctx, req ReqDTO) (RespDTO, error)`. Errors: `*kernel/errors.Error`; the service wrapper converts to the transport form decided by the Phase 1 spike (candidate: error string is JSON `{"code","message","details"}`; frontend helper `parseError`). Recorded in `docs/CONTRACTS.md`.
- DTOs: camelCase JSON, RFC3339 UTC times, `kernel/dto.ListRequest` in, `{items, nextCursor}` out. No generics in exported signatures if the spike shows the TS generator mangles them; otherwise `Page[T]` is allowed.
- Long-running: any mutation > 1s returns `{runId}` immediately. Progress via events + `RunsService.ListEvents(runId, sinceSeq, limit)`, `Get(runId)`, `Pause/Resume/Cancel(runId)`.
- Events: one Go registry `application/events` with typed constants and payload structs; `transport/wails/eventbridge` emits envelope `{type, seq, runId?, at, payload}`; a generator (`go run ./internal/transport/wails/gen`) writes `frontend/src/generated/events.ts` from the registry. Non-run events: `graph.changed{siteId}`, `pages.changed{siteId}`, `templates.changed`, `agent.delta{conversationId, messageId, seq, text}`, `agent.tool.started/finished{conversationId, callId, tool, args|result}`, `agent.confirm.requested{confirmationId, tool, args, risk}`, `app.locked/unlocked`.
- Agent chat: `AgentService.Send(conversationId, text) → {messageId}`, `Confirm(confirmationId, approve bool)`, `ListConversations`, `ListMessages(conversationId, cursor)`, `SetMode(conversationId, mode(confirm|autonomous))`.

### 16.2 Providers and the field registry

- Interfaces are declared by their consumers when the consumer exists. The observation use case (`application/observe`, called by the `sync_site` step) declares the readers: `CoreReader` (types, items of any public type with `_embed`, taxonomies, `/wp/v2/settings`), `StoreReader` (products with price, SKU, stock, categories, `meta_data`, variations, a product list, the shop, cart, checkout, account and terms page ids), `PluginReader` (manifest, bulk content with `since`, raw, filtered content, SEO meta, meta by key, a post's terms), `RenderReader` (`wp.Client.Visit`). The edit use case (`application/edit`, stage 3) declares the writers: a core writer (title, excerpt, featured image, a media item's alt and title, and the body on a site without the plugin), a store writer (a product's short description and first image, a variation's description, upsell and cross-sell ids, `meta_data` by key) and a plugin writer (the raw body, the SEO fields with their Open Graph twins, post meta by key), adapted from `*wp.Client` in `runtime/steps/edit_writers.go`. `Write` refuses a denied or unknown key, a read-only one (the H1), a product's title and a plugin field on a site without the plugin before anything leaves, asks for the plugin's guarded writes first, writes the core and store fields, then the meta and SEO fields, then the body, each under the value it read, and answers each key as written (with what the site stored), moved or held. `publish` makes one write per execution, so every write is recorded before the next.
- `field.Catalog` names every built-in field with its read source and write source as values (`core|store|plugin|render|none`) and whether it is denied; `field.Denied` is the hard-deny list: slug, regular and sale price, stock fields, SKU, the status and the parent of an existing page, categories and every taxonomy, the attributes a variable product's variations use. A custom meta key is a field the scope names.
- `sync_site` keeps its name and the `sync` kind; inside it the stages run per provider. The first observation of a site and one a person asks for walk the whole site; later ones are incremental through the plugin's `since` with a full walk every Nth observation (`observe.fullWalkEvery`), `since` being taken from the site's own stamps (the newest `modified` the previous walk saw, minus that walk's duration and a second), never from this PC's clock, which the server's may not share; a re-pulled item nothing changed on writes nothing; core without the plugin always walks fully, because `modified_after` filters on the site-local column. `sync_archive` archives after a full walk only. The render is visited for published pages whose identity or body changed (all on a full walk) with `Cache-Control: no-cache` and a nonce query argument; a draft is rendered through the plugin's preview link, else not rendered.

### 16.3 Blocks (`domain/block`)

- `Parse(raw string) Body{Kind, Blocks []Block}`: block-editor content when the raw holds `<!-- wp:`; classic content split on blank lines and on block-element boundaries (`document.go`'s `blockElements`); a shortcode or an unrecognised element (`div`, `section`, `table`, `iframe`, `script`, …) is one atomic `foreign` block kept byte for byte. `Block{Index, Kind(paragraph|heading|list|quote|html|shortcode|wp|foreign), Raw []byte, Hash, Attributes json.RawMessage}`.
- Operations: `Replace(i, html)`, `InsertAfter(i, html)`, `Delete(i)`, `RewriteRange(i, j, html)`, `PlaceLink(i, target, anchor)` (the linker chooses the block and anchor through `content.InsertTarget` over the whole document; `PlaceLink` writes the link into that block's bytes alone). `Serialize` concatenates untouched blocks' bytes exactly; each operation's result is parsed again and refused (`block_not_editable`) unless every untouched block comes back whole and in order and the body keeps its kind. No operation rewrites a block's markup (stage 3 dropped "reapplies the classes", having nothing to reapply); a block whose attributes hold the anchor, a dynamic block and a shortcode are refused. With `rewrites` on, our article takes the place of the client's first text block, his other text blocks go and every non-text block stays byte for byte. `Sanitize` strips the model's own classes and ids, never a block's implied ones.
- A write is `PutRaw(Serialize(body), expectedHash = base hash)`; the plugin answers the stored content and its hash, and the composed diff is carried onto that stored content through `block.Align` (`block.Landed`, stage 3): a block keeps its owner and takes the bytes and hash the site stored, a block the site's save added in a run of ours is the `site`'s and never ours, and one standing among the client's blocks stays his. The landed diff is the publish result's `blocks` and its ours are what `page_blocks_written` keeps, so "ours" survives what `wp_update_post` changes and a revert finds our blocks among the client's later edits. A relink and a revert record what the site stored the same way. **The client's blocks are the guard** (2026-10-19, the closing review of stage 2b): with `rewrites` off, every block we did not write is the client's, text or not; publish reads the site's body fresh with the blocks recorded as ours and writes only when the client's blocks on it equal the client's blocks the writer read, composing over the site's current bytes and recording our blocks straight after the raw write, so a retry composes the same body. In a block-editor body our part is one `core/html` block, so it never fuses with a client's freeform span. A relink splices (`block.Splice`): it keeps the bytes of every block whose render is unchanged, takes from the new render only the blocks the link changed or added, and carries `page_blocks_written` forward. Both the splice and the claim of our blocks (`block.Ours`) align blocks by their normalised render, and only a stored block matching the part we inserted, and no client block, is ours. An existing page is guarded on every write unless its scope or the run's confirmed pages say it rewrites; a body the writer never read counts as read empty, and a write whose answer was lost is recognised on the retry. The title, the excerpt, the SEO snippet and the short description are kept when their live value moved since the model read them. Whether a plain-text field moved (the title, the excerpt, the SEO title and description, and their Open Graph twins) is decided with HTML entities decoded and the value trimmed (`field.SameText`, the owner, 2026-10-23), so `&` stored as `&amp;` under a user without `unfiltered_html` is the same text: the observation agrees such a base to what the site stores and raises nothing, and no guard, check or comparison of a write pauses on it. What we write and every stored hash stay raw.

### 16.4 Raw versus render (`domain/render`)

- Three layers: the raw; the **filtered content**, `apply_filters('the_content', raw)`, which the plugin already computes in isolation for the H1 and answers on `GET /content/{id}/rendered` (theme-free, carrying what shortcodes and `the_content` snippets inject); the **public render** from `Visit`. Site-generated inside the content area is filtered minus raw; the theme is public minus filtered.
- `Extract(public, filtered string, body block.Body, site pagemap.Site) Extraction`: the content root is the smallest element of the public render holding the filtered content's word sequence (compared as `shown.go`'s `wordsOf` compares: entities decoded, punctuation and `wptexturize`'s quotes, dashes and ellipses dropped, case folded), never a selector. Root states, in this order: `archive` (a term page, the site's shop or its posts page, which the caller names: generated by the site from its items — a term archive, the shop, the posts page; its own text, if any, is a description that is read, never written; the root is where that text landed, else the landmark); `empty_raw` (the client's hubs today: the root is where the filtered content landed); `dynamic_only` (the raw is only shortcodes or dynamic blocks, a top-level block or a lone shortcode named in the site's `technicalBlocks` or `technicalShortcodes` counting as dynamic, whose expansion is region `content_dynamic`: content-owned, not editable, not site-generated); `found` (the root is located and the raw carries text); `not_found` (raw text the render cannot be found to hold). When the root is not located the `main`/`article` landmark is assumed and the state still follows the body: an empty raw is `empty_raw`, a raw of shortcodes and dynamic blocks `dynamic_only`, so `not_found` names text we cannot find and nothing else. Without the plugin the fallback is the raw blocks' word sequences, a root holding at least 60% of the text blocks.
- Regions in this order: JSON-LD (`BreadcrumbList` items name the breadcrumb element; `ItemList`/`CollectionPage` items name a listing), ARIA (`nav[aria-label*=breadcrumb]` case-insensitive; `header`, `footer`, `nav` landmarks outside `main` are navigation, the roles `banner`, `contentinfo`, `navigation` and `complementary` counting as `header`, `footer`, `nav` and `aside`, so a widget inside the page's footer is the footer's and a sidebar's own footer is not the page's), semantic (`main`, `article`, `h1`), a container with at least three links to product pages and at least two distinct products is a listing wherever it stands, inside the root or outside it (the related products under a product, an archive's grid in the assumed root), unless a landmark already claims it; a link whose `rel` names `tag`, `category` or `author` and that is not the content's own is navigation with the signal `rel` (a post's author and category, a product's categories); the rest `unknown`. A link to the document itself (a fragment, a query, or the page's own path with either) is no page link at all. Every link gets a type, a region and a resolved target page. Facts kept: every trail (names, paths and each linked crumb's href as it was written, in order, from each `BreadcrumbList` and each breadcrumb nav), JSON-LD objects by type (`Product`, `WebPage`, `CollectionPage`, `ItemList`, `BreadcrumbList`), headings, word counts of content and of generated text, the builder detected (a settings default lists the builders' class prefixes, data attributes and shortcode prefixes), the majority URL form of the page's hrefs, the page's robots meta, and whether the theme prints an H1 (`printed` when an `<h1>` stands outside a located root, or inside it with text the raw does not hold; `absent` when neither; unknown when the root was only assumed). A `BreadcrumbList` item names its crumb by `item` as a string, by `item.@id`, `item.url` and `item.name`, or by its own `name` and `url`; `position` is a number or a string; the objects of a `@graph` count one by one.

### 16.5 Hierarchy and technical pages

- `pagemap.DeriveParent(page, signals, index) Derivation` (signals: the trails, the WordPress parent, and where each modelled page's own visit landed): a trail is its crumbs before the page's own, minus any technical page; its nearest remaining crumb resolves, in this order (the method is stored beside the reason, `pages.parent_method`): **by its link** against every modelled page of every type, term pages included, a modelled page whose own visit lands on another page being followed to it (`href`, or `redirect` when followed); **through its redirect**, when its internal link resolves to nothing: the render stage looks the link up once (one anonymous HEAD through the client's limiter and the site's User-Agent, a GET closed unread on 405 or 501, stopping at the first off-site hop) and keeps the final path and status on the crumb, and the landing counts only when it is neither the root, the page nor a descendant and its title, H1 or term name carries the crumb's name, because WordPress's 404 guesser redirects a dead slug to any similar one (`redirect`); **by its exact name**, only when the crumb has no link or its internal link is dead (an error status after redirects), against the observed titles, H1s and term names under `graph.Key` after HTML entities are decoded, the page, its descendants and archived pages excluded. The candidates split into regular pages (any type but a term, products included) and term pages: one regular page resolves (`name`), and when term pages share its name an informational `parent_name_twin` names the crumb, the page taken and the term twins, the page being the one we write and link to while the archive belongs to the store; two or more regular pages raise `parent_ambiguous` naming them; with no regular page one term page resolves and several are `parent_ambiguous` (the owner's ruling of 2026-10-18). A live link to a page the model lacks, or an external one, never falls to its name. A nearest crumb that resolves to nothing yields a `parent_unresolved` finding naming it and the derivation falls to the next **source**, never to the next crumb. A crumb at the site root resolves to the front page when one is modelled and is dropped otherwise; a trail whose nearest crumb is the front page is weak evidence: the other trails are tried, then the WordPress parent, and only then the front page with that trail's reason. **The front page is the root**: not technical, no parent, and the target every trail starts at. A parent loop the trails make is broken at its first on-site path, which is derived again without trails (repeated until no loop remains, else no parent) and named by `parent_cycle`. Several `BreadcrumbList` objects: the one with the most resolving crumbs wins, a tie to the one matching the visible nav, else the first. A breadcrumb nav is a `nav` whose `aria-label` contains "breadcrumb" (case-insensitive) or whose `itemtype` names `BreadcrumbList`, since a theme may mark its breadcrumb with microdata alone; one trail per nav: the first `ol`/`ul` with at least two items, else the nav's links in document order plus a trailing non-link text as the current page, since WooCommerce's own breadcrumb is a run of links with slash separators. A crumb at the site root is dropped as the front page is, whatever the front page shows. A `product_cat` term page may be a parent (the owner's answer 4); `BuildTree`, the orphan rule and `blockerOf` treat it as a page already on the site. Then the WordPress parent → `wp_parent`; then `Index.PathParentID` → `url`; else none.
- Nothing writes a parent to an existing page: `repair_hierarchy` goes (the `repair` kind loses its recipe and leaves `runKinds` in `vocab.ts`; the `CHECK` keeps the word), `publish_parent` shrinks to the creation-only lookup (the owner's answer 1: the one creation call of a planned page may set status, parent and slug, recorded in the artifact), `publish` sends neither slug nor parent on an update, and `publish.compare` and `runs.start.parentOf` read the derived parent and the identity snapshot instead of `ParentPath(child.Path)` and the path-derived slug.
- Technical pages: `page_for_posts`, `wp_page_for_privacy_policy`; WooCommerce's shop, cart, checkout, account and terms page ids; cart, checkout and account shortcodes or blocks in the raw (a settings default lists them); `noindex` in the render's robots meta, which every SEO plugin writes and the companion's SEO meta does not carry; a workbook's `own_entity: no`; a person's `manual`. The observation never overwrites `workbook` or `manual`. A finding option clears or sets it. Nothing makes the site root a WordPress parent on a creation, whatever the derivation says for the tree.

### 16.6 Page types and the migration from `kind`

- Presets with their role in the network: hub (links down and sideways, a children section), store category (`store_category`, a WooCommerce term archive: read-only, nothing writable), catalog (the shop or listing root), product (short and long description, no children section), entity (an article: up and sideways), technical (no links, never generated). The word "Category" is the client's (the owner's ruling of 2026-10-18): a regular page his sheet, entity kind or template kind calls a category is a hub, and a `product_cat` page is a store category whatever its cell says. A site's set is seeded on its first observation; the client renames and adds types in Settings → Page types. A seeded Hub, Entity or Product type points at the built-in Hub, Guide or Product template (the owner's ruling of 2026-10-20) unless the site has a default template a person chose, which a type's template would otherwise override; a type a person creates from a preset inherits its built-in unless the request names another or none; migration 0066 backfilled the types that had none on sites without a default.
- Migration: `page_types` seeded; `pages.page_type_id` backfilled by the template's `PageKind` where a template is assigned, else by the entity's kind (hub→hub, category on a regular page→hub, product→product, topic→entity, custom→entity, the owner's answer 2), a `product` page→product, a `product_cat` page→store category, every other page→entity; `technical` comes only from `technical_reason`. A later migration drops `entities.kind` by the 0030 rebuild and `templates.page_kind`. The import's kind cell maps to a type by the site's own type names first and synonyms second, and the export writes the type's name.

### 16.7 The context pack and the writer

- `contextpack.Build(facts, scope) Pack` with sections in priority order: identity and type (1), the field's instruction and policy (1), the entity card (2), the field's current value (2), keywords and anchors (3), the trail with ancestor summaries (3), notes (3), link targets with summaries (4), listed products' facts (4 for hub, catalog and store category types, 6 otherwise), siblings' coverage (5), children (5), other fields (6), the generated-regions summary (6). `Fit(pack, budget)` drops the lowest priority first and trims lists from the tail (products and siblings by shared keywords, then score); priority 1 is never dropped, and a budget below it is refused (`budget_too_small`). The budget is a role setting, `llm.inputBudget.<role>`, defaulting to the model's context window less the output ceiling, the effort's reasoning allowance and the stable prompt, and refused in preflight when it cannot carry priority 1 (`input_budget_too_small`); the token estimate is `domain/llm.Tokens`, which `budget.go` calls too. A page's summary is its meta description, else its excerpt, else the first sentence of its body, else a structural summary built from the model ("Hub for Peptides under Home; lists A, B and 3 more; its children are …"), never a model call.
- **Name twins** (the owner, 2026-10-19). A hub page and a store category of one name are one node: a link target on the archive moves to the hub (`content.PlanLinks`, so every caller agrees), a target that becomes the page itself is dropped and duplicates merge, and a hub's pack carries its twin's products (from `page_terms`) when its own listing is smaller. **Our links take the site's form**: the majority of its own contextual links, ours left out, else the theme's `url_form`, else the site setting; `LinkTarget.URL` stays the path and `LinkContext.Href` gives the form.
- The writer steps keep their names and artifacts: `generate_body` (Draft and BodyHTML) and `generate_meta` (Meta) consume the pack; a new template step `generate_fields` (artifact `fields`, the editor's role) answers in one structured call the enabled, AI-written fields `publish` writes: the excerpt, where the post type supports one, and a product's short description (since 2026-10-20, out of `generate_body`'s answer), asked only where the template's `product.shortDescription` is enabled too and briefed by its intent, words and keyword rule, answered as plain text and written as escaped paragraphs, and every variation's description in the same call, read from the model's `variation:<id>` rows and named by its options; stage 3 widens it as its field writers land. The writer leaves the client's own paragraphs alone unless the scope's `rewrites` switch is on for that page type and field, off by default: his blocks (the current ones whose hash `page_blocks_written` does not hold) are kept byte for byte and ours are added after his last text block, written through the raw route against the hash the writer read, a conflict pausing the item. A run may switch rewriting on for chosen pages, with the user's confirmation in the run-start dialog (the owner's answer 5). **Our H1 goes in only where the observation shows that none is printed** (the owner, 2026-10-23), one rule for every page: over an existing page when its own render's `theme_h1` is `absent` and none of the client's blocks that stay holds an H1, on a page we create when every observed render of its WordPress type is `absent`, and never without an observation. `publish` plans what it will write over in a first execution and makes one write per execution after it, each recorded before the next, so a pause, a failure or a lost answer leaves every write it made revertible; the `fields` artifact keeps the answer, so a retried publish never asks the model again. **An existing page's status is never written** (the owner, 2026-10-20), and in a draft-mode run nothing reaches an existing page until a person accepts its diff: `publish`, `relink_page` and `relink_neighbors` pause the item `awaiting_review` with an `edit_plan` (each field before and after, each block kept, added or removed and whose), an acceptance writes only the plan shown and is refused when the agent asks for it, and a plan that moved is shown again. A person may accept a page's review field by field (the owner, 2026-10-22): a field left unticked, the body included, is not written, not recorded as ours, and named in the publish result's `declined`; a review that changes bodies only is accepted whole. A link target is on the site only when it is published, so no neighbour links to a page we created as a draft. The link plan runs per page type and field policy; `Sanitize` keeps the links a field's policy and the plan allow; `Compliance` and the audit owe contextual links only and count the rest. Link rules live in the field scopes; `template.LinkPolicy`, `link_policies`, `site.defaults.linkPolicyId`, the `policies_*` tools and the Policies screen go in stage 2, each preset's default scope carrying the former default rules; `templates_set_override` stays.
- **One root, two views** (the owner, 2026-10-19). The writer and the in-app agent read the site model through one layer of read functions (`domain/contextpack` over a snapshot that `application/sitemodel` alone loads): a page's identity and type, its entity card, its trail, children and siblings with what each covers, its listed products, terms, keywords and anchors, link targets, links in and out by type, fields with their scopes, the regions' summary, notes and open findings. The writer's view is the fitted pack above, sent with every writing call. The agent's view is a short site brief built once per conversation (the types with counts, the top of the hub tree, content and link health, orphans, findings by code), kept in its instructions under a prompt cache key, `pages_get` for one page (since 4.2: `sitemodel.Page`, the page view's neighborhood with the identity, the type and its source, the parent's reason, method and trail, fields with current, base, hash and owner, the body in sum by owner, open findings with ids and options, and the template a run would use with its source; it replaced `sites_explore`'s `page` view and `templates_resolve_for_page`), and one query tool, `sites_explore`, whose views are `tree`, `links`, `gaps` and `pack`, the last being exactly what the writer would see. Neither view computes anything the other computes differently. **The agent edits through the model** (2026-10-23, 4.2): `pages_fields` and `pages_blocks` read a page's fields and blocks with their owners (`sitemodel.Fields`, `sitemodel.Blocks`) and write one field or one block, each write a one-item run of the kind `edit` whose step `edit_page` takes relink's path for a block and the registry for a field and leaves a version-3 publish result the revert reads; the write waits for the person in either mode and is refused before the card when its field is denied, read-only or a person's, its hash moved, or it would replace or delete the owner's block without rewrites. **A run scoped to fields keeps only the steps they need** (4.2, `run.ScopeRecipe`): the body's steps for the body, `generate_meta` for the SEO pair, `generate_fields` for the rest, a title without the body included; publish requires only its fields' drafts and, without the body, writes none, and the estimate prices the kept steps alone. The agent proposes entity cards from the read layer and its own knowledge; a card is written only once a person accepts it. These read tools move here from stage 4, which keeps the findings inbox, its resolution tools and the matcher.
