### Decided at the plan

1. **Where the H1 was lost.** The `h1` field was written only from the content's first `<h1>` (`observe/pull.go`, `observe/content.go`). On Blocksy the theme prints the title as the page's H1 before `.entry-content`, outside the content root, so the field stayed empty; the extraction saw that H1 (`ThemeH1Printed`) but never kept its text, and the stored extraction keeps only the headings inside the root.
2. **The visible H1.** The extraction records `H1` and `H1Source` (`content`, `theme`, `none`): the first visible `<h1>` in document order outside the site's banner, navigation, sidebars and footer, `content` when it sits inside the root with text the raw content holds, `theme` otherwise, unknown when the root was not located or the visit landed elsewhere.
3. **One rule, one value.** `render.VisibleH1(record, contentH1)`: a render with a known source wins, else the plugin's or core's content H1 as `content`, else `none`, never a guess. The content stage applies it with the stored render, the render stage after each extraction, so no walk flips the field. `pages.h1` stays the planned H1 and follows the observed one only where it still equals the previous observed value (`PageRepo.FollowObservedH1`), so `hasPlan` keeps reading a workbook's H1 as planned.
4. **A read-only field is always agreed.** `field_changed_on_site` protects what we may write; the H1 is never written.
5. **Pages synced on 2.5.0.** 0075 fills the source of every render whose theme prints no H1 from its stored headings; a theme-printed or unknown render is fetched again on the next ordinary sync, and only those, because its text was never stored.
6. **One chat in the site's context.** The rail's Agent opens `/s/:siteId/agent`, the same conversation the dock holds for that site; `/agent` exists only with no site selected and says that site tools need one.
7. **The proposal drawer's state** lives in a module store keyed by site and opener, cleared on accept, on Reset, on a different findings seed and on restart. **Amended the same day by the owner**: the dialog's redesign moves into this session, editing included. The redesign covers a near full-window dialog, the proposals as a tree with cascading selection and a partial state, select all and select none, search that keeps ancestors visible, and editing a proposal's name, parent and keywords before accepting. Every part of it is kept in the same store. `ApplyProposals` already takes the proposals as the screen holds them, so it needs no Go change.
8. **The three layouts** collapse columns by measured width as the Site map does, and each gets a `fits` step.

#### Decided while building

- **The source does not wait on a located root**: a visitor sees the h1 either way, so it is `content` or `theme` whenever the render holds one.
- **The stands prove the upgrade through the repositories**: the store exposes no migration control, so the e2e test takes the themed rows back to what 2.5.0 stored; the migration test proves 0074 to 0075 itself.
- **Store categories get their H1 too**: the content stage never wrote one for a term, and the render shows it.
